# Анализ системы компании в контексте планирования логирования.

## Из каких систем требуется сбор логов:

- Shop API
- CRM API
- MES API

## Список необходимых логов с уровнем INFO.

- Смена статусов(время, id пользователя, id заказа)
- Входящие/исходящие запросы(время, id пользователя, id заказа)
- Загрузка файлов(время, id пользователя, id заказа, размер файла)
- Расчет стоимости(время, id пользователя, id заказа)
- авторизация пользователей(время, id пользователя)

## Использование других уровней логирования

- FATAL - при отказе сервиса
- ERROR - ошибочные действия
- WARN - нестандартное поведение (неправильный пароль)
- DEBUG - на дев среде для отладки

# Мотивация

## Добавление логирования даст компании:

- сокращение времени на выявления причины инцидента
- выявление узких мест системы
- мониторинг доступности сервисов

## технические и бизнес-метрики решения

- время выполнения запросов
- время перехода статуса заказа
- размер файлов
- количество запросов пользователя
- стоимость заказов пользователей
- время выполнения заказа

## Приоритет введение логирования

Покрыть логированием всю систему сразу нецелесообразно и добавит излишнюю нагрузку,
в первые 0-3 месяца необходимо добавить логирование в следующие процессы, что бы найти причину зависших заказов:

1. процессы по созданию заказов
2. процессы расчета стоимости
3. процессы назначения заказов на исполнение

# Предлагаемое решение

внедрение инструментов из стека ELK:

- Filebeat передаёт данные в Logstach — конвейер данных.
- Logstach передаёт данные в Elasticsearch — базу данных.
- Elasticsearch обменивается данными с Kibana, инструментом для визуализации.

## Политика безопасности в отношении логов

- Разделение доступа через RBAC в Kibana
- Не использовать в логах чувствительных данных(персональные и платежные)
- Всегда используйте шифрование (SSL/TLS) для передачи логов на внешние системы и хранилища.
- Реализуйте шифрование логов на стороне сервера перед сохранением их на диск, чтобы предотвратить доступ к
  конфиденциальным данным.
- Настройте ротацию логов по времени (например, ежедневно) или по объёму (например, при достижении определённого размера
  файла).
- Архивируйте и сжимайте устаревшие логи для долгосрочного хранения, используя внешние хранилища (допустим, Amazon S3,
  Google Cloud Storage).

## Политика хранения в отношении логов

- отдельный индекс под систему на сервис
- хранение логов ограничить по дням для каждого окружения отдельно
    - Dev: 7 дней. (до 2GB на день)
    - Release: 30 дней. (до 5GB на день)
    - Prod: 90 дней (для аудита и анализа) (до 10GB на день).

# необходимые мероприятия для превращения системы сбора логов в систему анализа логов

- Настройте уведомления в реальном времени для выявления аномальной активности, связанной с этими событиями.
    - Резкий рост ошибок (>5% от запросов).
    - Аномалии в количестве заказов (например, DDoS).
    - Превышение времени ответа критичных endpoints (>5 сек).
